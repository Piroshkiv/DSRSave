# DS1R DLC NPC Quest Flags — Marvellous Chester, Dusk of Oolacile, Elizabeth the Mushroom, Quelaag's Sister/Fair Lady, Hawkeye Gough

Companion to `boss-flags.md`/`npc-flags.md`. Status legend matches those docs:
**CONFIRMED (code)** / **CANDIDATE** / **STRUCTURAL (high confidence, not byte-proven)** / **OPEN**.

## Headline result: a NEW flag region (region 7) was discovered this session, but its subbank `k` could NOT be reliably pinned down — do not trust any specific byte/bit below without further work

Every quest-stage flag found for these 5 NPCs' own personal milestones (as opposed to their simple Template-A/B death flags, which ARE region0 and fully solid) uses flag IDs starting with digit **7** (e.g. `71800020`, `71600004`, `71810050`, `71410035`), which decodes to **region=7** — a region this project had anticipated in its formula code (`region7_base(k) = 70400 + k*1280` already existed in `decode_gwyndolin_n26.py`) but never actually needed until now.

**A blind brute-force of `k=0..29` across regions `{1,5,6,7}`, checked against every shipped NPC's bits, produced many "matches" — almost all of which are statistical noise, not real identifications.** This is the exact same trap the project's own memory already warned about (Session N+17/18's boss-bit correlation mining: too wide a search space, too few corroborating hits per candidate, no second independent signal). Checked this directly: the one candidate that looked most promising (`71600004` → `pattern1+0x13156 bit3`, matching Marvellous Chester's shipped bit) was the ONLY match out of 35 sibling flags tried under the same `(region=7, k=6)` — if that `k` were actually correct, several more of Chester's own 8 shipped bits should also land correctly, and none did. **Treat this as an unconfirmed coincidence, not a real finding.** None of the other "matches" fared any better on a second check.

**Practical conclusion: resolving region 7's subbank `k` values needs either (a) a live before/after save diff anchored to a KNOWN true/false state** (the method that worked for Gwyndolin's corridor flag in Session N+29 — it only works because we independently knew his combat-form death flag was already true for that test character, giving a reliable anchor; we have no equivalent known-true/false anchor for any of these 5 DLC NPCs in the current save), **or (b) finding the EMEVD/ESD-side consumer of one of these flags whose OWN already-confirmed byte can cross-validate it, same as Session N+23's roster-byte method.** Neither was achieved this session — every byte/bit cited below for a "personal milestone" flag (the `718xxxxx`/`716xxxxx` family) is **OPEN**, not candidate-grade. Only the Template-A/B death flags (region0, no `k` needed) are solid.

## Per-NPC findings

### Marvellous Chester
- **Identity REVISED after the `SetTeamTypeAndExitStandbyAnimation` retry (see Aggro section below) — likely NOT in `m18_00_00_00` at all.** Found a strong new lead: entity `6730` (unique `c4090` model, in `m12_01_00_00`, the Royal Wood transition area — same map as Hawkeye Gough) has its own hostility flag that decodes to `pattern1+0x13D bit6`, landing exactly BETWEEN Chester's two existing shipped bits at that same byte (`0x13D bit5`/`bit7`). This is a much stronger, non-brute-force signal than anything found for the original `c5330`-in-`m18_00` guess. **Treat entity `6730` in `m12_01_00_00` as the leading candidate for Chester now; the original `c5330` guess below (for Dusk's section) should be considered likely wrong for Chester specifically.**
- Shipped bits (8 total: `0x13D`b5/b7, `0x238F`b0, `0x2395`b6, `0x239A`b7, `0x13156`b3, `0x16D70`b4, `0x16DBE`b7) are scattered across unrelated byte ranges — consistent with him being an itinerant NPC whose tracking spans multiple unrelated systems/areas, not one single quest cluster. None individually traced this session.
- **Hostility mechanic found** (corrected — see Aggro section): his own flag `1841` → `pattern1+0x13D bit6`, via the shared template event `11210510`, called from `m12_01_00_00` event `50` as `RunEvent(1, 11210510, 6730, 1841)`. **CANDIDATE**, strong structural support, not yet shipped or in-game tested.

### Dusk of Oolacile ("Revive golem")

- **"(Revive golem)" label explained — STRUCTURAL finding, high confidence, not byte-proven**: `m18_00_00_00`'s MSB has two previously-unidentified non-talkable models, `c3490` (entity `1803900`) and `c3491` (entities `1803901`/`1803902`) — these are almost certainly the **crystal golem(s) that imprison Dusk**, which the player must destroy to free her (standard DS1 mechanic). The shipped label is most plausibly a maintainer's note that reverting her captivity state may also require resetting the golem's own kill-state, not a mistranslation. **Not traced to a specific flag this session** — would need the golem entities' own death-flag (same Template-A/B scan method, applied to `1803900`-`1803902`) to confirm and give an exact byte.
- Her large shipped bit list (16 bits, including 3 shared verbatim with Elizabeth: `0x141`b7, `0x142`b1, `0x2395`b5) was not individually traced.
- No `SetTeamType` evidence checked specifically for her (time did not permit; flag as unexplored, not confirmed-absent).

### Elizabeth the Mushroom
- Found in `m18_01_00_00` (Oolacile Sanctuary Garden), as a **two-entity pair**: entity `6023` (talkable, `talk_id=181602`) and entity `6024` (non-talkable). This exact "talkable decoy + separate combat form" structure is the SAME pattern already confirmed for Gwyndolin (Session N+26) — **STRUCTURAL, high confidence**: this is almost certainly Elizabeth's real "turns hostile and fights back if attacked" mechanic (a known DS1 behavior for her).
- At map load (`m18_01`'s event `50`), entity `6024` is explicitly disabled (`SetCharacterState(6024, 0)`) and set to team type `9` (hostile) in the SAME two instructions, unconditionally — i.e. her combat form is pre-configured as hostile but dormant, then presumably enabled via one of the map's `RunEvent` calls into the standard Template-A/B death-handler (`11810520`→entity `6023`, flags `[1060,1074,1073]`; `11810531`/`11810532`→entity `6024`, flags `[1060,1074,1061]`/`[1060,1074,1062]`) once provoked — **this is the project's clearest aggro/hostility finding this session, and it's a `SetTeamType` mechanic exactly as the coordinator predicted.**
- These death-template flags (`1060`-`1062`, `1073`-`1074`, all region0) decode cleanly (`pattern1+0xD7 bit1/2/3`, `pattern1+0xDD bit5/6`) but **do NOT match any of Elizabeth's 4 shipped bits** — meaning either her shipped tracking doesn't yet cover this specific hostility mechanic at all (a real gap, worth adding), or entity `6023`/`6024` isn't actually Elizabeth (see identity caveat below). Flagging as **CANDIDATE new bits to add**, not yet cross-confirmed.
- Her own personal milestone flags (`71810050`-`71810053`, `11810590`-`11810592`, region 7/region 1 respectively) are **OPEN** per the region-7/k caveat above.
- **Identity caveat**: entity `6023`/`6024` is assigned to "Elizabeth" by elimination (only remaining talkable NPC in the only remaining DLC hub map) and by the hostility-mechanic match to her known game behavior — not by an exact-bit cross-check (none of her 4 shipped bits were independently matched to anything found this session). Reasonably confident, not proven.

### Quelaag's Sister / The Fair Lady (Fire Keeper)
- Found in `m14_01_00_00` (Quelaag's Domain), entity `6002`, `talk_id=141600` — the only low-numbered talkable candidate in that map, **STRUCTURAL identification** (not exact-bit-confirmed).
- **Checked for a Quelaag-death dependency — structurally impossible via a direct flag read, this is a real and useful negative finding, not a gap**: Quelaag's own "killed" bit (`pattern1+0x55 bit6`) lives in `GameDataMan`'s separate `block1` struct, which is NOT part of the EventFlag buffer at all (established repeatedly throughout this project, e.g. `boss-flags.md`'s own formula notes). Her Talk ESD can only call `GetFlagState`/`GetEventFlagValue`-style EventFlag reads — **it has no native command capable of reading Quelaag's block1 bit directly**. So if the Fair Lady's dialogue or availability does change after Quelaag's death in actual gameplay, it must be through some OTHER mechanism this session didn't find (e.g. a dedicated native condition, or simply her dialogue doesn't change at all and the premise should be re-checked with the user). **No `SetFlagState`/`SetEventFlagRange` call in her ESD referenced anything resembling a cross-check on Quelaag specifically.**
- No `SetTeamType` calls found anywhere in `m14_01_00_00.emevd.dcx` at all (zero, for any entity) — she has no scripted hostility mechanic.
- Her 7 shipped bits (`0x65`b3, `0xF4`b7, `0xF5`b1, `0x3795`b6, `0x37BA`b7, `0x16D7F`b1, `0x16FA2`b0) were not individually traced this session (her own ESD's 14 flag writes are all region-7 `714100xx`-family, same OPEN caveat).

A parallel fork (Griggs/Logan) found that the real project-wide "flip to hostile" instruction is often **`SetTeamTypeAndExitStandbyAnimation`** ((2004,44), same args shape: `character, team_type`). Retried with that instruction — it changes several conclusions below. **Lesson for future sessions: always check BOTH `(2004,2)` and `(2004,44)` for any hostility search in this game, never just one.**

**Correction to the Fair Lady finding**: `m14_01_00_00` DOES have 5 `SetTeamTypeAndExitStandbyAnimation` calls, but ALL target entity **`6004`**, not her candidate entity `6002`. Traced the literal (non-templated) call in event `11410531`: gated by `IfCharacterRegionState(..., 10000, 1412510)` — a **player-enters-a-trigger-region ambush**, not a "you attacked her" retaliation. The companion event `11410541` (a DIFFERENT team type, `12`, likely "neutral"/"revert" rather than hostile) checks `IfCharacterDeathState` on four entities (`1410410`-`1410413`, the Demon Firesage/Centipede Demon boss-arena range per Sessions N+22-24) — this whole cluster is almost certainly a **generic hidden-ambush mob near the boss arenas**, unrelated to Fair Lady. Her own entity (`6002`) still has zero hostility calls under either instruction name — the original "no mechanic for her" conclusion stands, just stated more precisely now (the earlier "zero calls in her whole map" phrasing was imprecise; there ARE such calls in that large shared map, just not targeting her).

**Side finding, partially resolved**: the generic "become hostile if attacked" EMEVD template turns out to exist in (at least) TWO variants project-wide — a plain-`SetTeamType` copy (`m18_00`'s `11800510`, `m18_01`'s `11810510`) and a `SetTeamTypeAndExitStandbyAnimation` copy (`m12_01`'s `11210510`, `m14_01`'s `11410510`/`11410501`). The `m12_01`/`m14_01` copies DO have real `RunEvent` callers (shown above) — that's what unblocked the Gough/Ciaran/Chester findings. The `m18_00`/`m18_01` plain-`SetTeamType` copies STILL have no findable caller anywhere (checked both own maps and `common.emevd.dcx`, for both instruction variants) — remains **OPEN**.
