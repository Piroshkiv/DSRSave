# DS1R — находки статического реверса DarkSoulsRemastered.exe

Рабочий журнал сессии: ищем код чтения/записи сейва прямо в бинарнике
(`DarkSoulsRemastered.exe`, таймстамп линковки 2022-10-11, файл датирован
13.01.2026 — т.е. текущий патч), чтобы перестать гадать байт-оффсеты и
опираться на реальный код. Инструменты: `pefile` + `capstone` (чистый Python,
без запуска стороннего кода — загруженный `radare2.exe` харнесс заблокировал,
это ожидаемо и правильно).

Формат: только проверенные дизассемблером факты. Гипотезы помечены явно.

## TL;DR

- `.co2` (Seamless Co-op) и `.sl2` — **один и тот же формат байт-в-байт**.
  Подтверждено эмпирически: `DRAKS0005.co2` расшифровался тем же ключом/IV-схемой,
  что и ванильный `.sl2`, и дал читаемое имя персонажа и разумный уровень.
  Мод просто переименовывает файл, чтобы не смешивать сейвы с ванильными
  (подтверждено и описаниями мода в сети).
- Нашёл **MD5Init** живьём в коде (адрес ниже) — байты "AES_KEY" из
  `constants.ts` это ровно стандартные магические константы MD5 (A/B/C/D).
  Как литерал (16 байт подряд) этот ключ **не встречается больше нигде**
  в экзешнике — только эти 4 инициализирующих значения внутри MD5Init.
  Гипотеза (не подтверждена до конца): Rijndael-ключ не хранится статикой,
  а берётся как побочный эффект вызова `MD5_Init(&ctx)` — байты `ctx.state`
  используются как 16-байтный AES-ключ напрямую, без `Update`/`Final`.
- Нашли класс шифра по RTTI: `class DLCR::AES::DLRijndaelAlgorithm`
  (`DLCR` — внутренний неймспейс крипто-кода движка). AES — чистый софт
  (НЕ AES-NI: ни одной инструкции `aesenc/aesdec/aeskeygenassist` в бинаре),
  и НЕ через `CryptoAPI`/`BCrypt` (их нет в таблице импорта вообще).
- Подтвердил живьём цепочку указателей `PGD = [[BaseB]+0x10]`, которой
  пользуются существующие комментарии в `Character.ts` (взятые из
  `1FRDarkSoulsRemastered.CT`). Конкретное место использования, которое я
  дизассемблировал, оказалось сеттером цвета волос/глаз (UI character
  creator), не кодом записи сейва — но цепочка подтверждена байт-в-байт.
- `Pattern1` (`FF FF FF FF 00 00 00 00 ×2`, см. `findPattern1()`) оказался
  **не уникальным маркером**, а общеупотребимым заполнителем: в реальном
  расшифрованном слоте он встречается **48–86 раз** в том самом окне
  `0x1F000–0x1FFFF`, где его ищет текущий код. Отсюда и ощущение "мне не
  нравится мой поиск паттерна" — он структурно шаткий. См. раздел ниже.
  (Для справки: `docs/ds3-bonfire-anchor.md` описывает тот же P16-паттерн
  для DS3 и тоже требует "последнее вхождение в окне + фиксированный
  relative-оффсет" — т.е. это известная, но терпимая проблема во всей
  линейке редакторов, а не баг конкретно DS1.)
- `.sl2` как строка встречается в экзе **один раз**, и ведёт не к автосейву,
  а к мёртвому/отладочному коду Windows `IFileDialog` (COM, видно по
  `CoCreateInstance`/`CoInitialize` в импортах) — конструктор
  `COMDLG_FILTERSPEC`-подобной структуры с фильтром `"*.sl2"`. Тупик для
  поиска реального кода записи.
- `ds1sc_launcher.exe` — тонкий стаб (193 КБ), только грузит `ds1sc.dll`,
  никакой логики путей/форматов сейва в нём нет.
- `SeamlessCoop/ds1sc.dll` — не трогает формат сейва напрямую (нет строк
  `PlayerGameData`/`SaveLoad` и т.п.). Внутри — встроенный дизассемблер
  (похоже на Zydis, судя по строкам мнемоник типа `xsaveopt64`, `rdrand`) и
  `libcurl`/schannel (для сетевого кода кооператива). Единственная полезная
  находка — кусок таблицы RTTI-имён игры: `NS_FRPG::PlayerIns`,
  `NS_FRPG::EcTest*` (классы условий EzState-скриптов). Подтверждает нейминг
  (`NS_FRPG` — неймспейс игровой логики, `DLCR` — неймспейс крипто), но не
  даёт зацепок по структуре сейва.

## Детали

### 1. MD5Init (подтверждено дизассемблером)

```
VA 0x140d0f1a0:
  xor  eax, eax
  mov  dword [rcx+8],  0x67452301      ; state[0] = A
  mov  qword [rcx],    rax             ; count_lo/count_hi = 0
  mov  dword [rcx+0xc],0xefcdab89      ; state[1] = B
  mov  dword [rcx+0x10],0x98badcfe     ; state[2] = C
  mov  dword [rcx+0x14],0x10325476     ; state[3] = D
  ret
```

Структура контекста: `{count_lo, count_hi, state[4], buffer[64]}` — стандартный
layout MD5_CTX. Сразу следом (`0x140d0f1d0`) — похоже на `MD5_Update`
(буферизация по 64 байта, зовёт `0x1410e593c` и `0x140d0f530` —
по всей видимости `MD5_Transform`).

Нашёл 6 вызовов `call 0x140d0f1a0` во всём экзе — везде паттерн
`Init → Update → Final` для хэширования произвольных данных (похоже на
общую утилитную функцию движка, не специфичную для сейвов). Ни в одном
месте результат не передаётся напрямую в код, похожий на Rijndael/AES —
но это не исключает, что ДРУГОЙ вызов (который мы не нашли) берёт
`ctx+8` (адрес `state`) и передаёт как указатель на ключ в
`DLRijndaelAlgorithm::SetKey` без вызова Update/Final.

**Эмпирическая проверка, что ключ (01 23 45 67 89 AB CD EF FE DC BA 98 76
54 32 10) правильный**: расшифровка реального `DRAKS0005.sl2`/`.co2` этим
ключом (AES-128-CBC, IV = сохранённый "checksum") даёт читаемое имя
персонажа и разумные значения level/HP — для AES-CBC с неправильным
ключом это невозможно получить случайно.

**Не найдено:** эти 16 байт как единый литерал — ни в `.rdata`, ни в
`.data`, ни где-либо ещё (проверено `pefile.get_memory_mapped_image()` по
всем секциям + сырой файл). Каждое из 4 слов (`0x67452301` и т.д.)
встречается ровно 1 раз во всём экзе — и это единственное место выше.

**Следующий шаг (не сделан):** найти RTTI Complete Object Locator для
`DLRijndaelAlgorithm` → его vtable → метод `SetKey`/конструктор → откуда
вызывается и что передаёт как key-буфер. Моя первая попытка через COL
(x64 RTTI: `signature, offset, cdOffset, pTypeDescriptor(RVA), ...`)
не нашла совпадений — возможно, неверно вычислил смещение
TypeDescriptor-структуры относительно найденной строки имени; не доведено
до конца.

### 2. Класс шифра

RTTI-имя найдено как ASCII и UTF-16 строка:

```
.?AVDLRijndaelAlgorithm@AES@DLCR@@
```

Демангл: `class DLCR::AES::DLRijndaelAlgorithm`. Нет инструкций AES-NI
(`aesenc`/`aesdec`/`aesenclast`/`aesdeclast`/`aesimc`/`aeskeygenassist` — 0
совпадений во всём `.text`), нет импортов `CryptEncrypt`/`BCrypt*`
(в `ADVAPI32.dll` только `SystemFunction036` (=`RtlGenRandom`) и
`GetUserNameW` — не относится к шифрованию сейва). Значит это чистая
софт-реализация Rijndael, написанная/слинкованная прямо в движок.

### 3. Цепочка PGD (подтверждена живым дизассемблером)

Якорь из `1FRDarkSoulsRemastered.CT` (`BASEB_AOB` в
`tools/ds1-gesture-sweeper/constants.py`) резолвится в текущем билде
по адресу `VA 0x14072bb30`:

```
0x14072bb30: mov  rax, [rip+0x155e9f9]   ; rax = [BaseB]
0x14072bb37: xor  r13d, r13d
0x14072bb3a: mov  rsi, rcx               ; this
0x14072bb3d: test rax, rax
0x14072bb40: je   0x14072bd99            ; null-check
0x14072bb46: mov  rax, [rax+0x10]        ; PGD = [[BaseB]+0x10]  <-- подтверждено
0x14072bb4a: test rax, rax
0x14072bb4d: je   0x14072bd99
0x14072bb53: movd xmm0, [rax+0x5b0]      ; дальше — похоже на UI-сеттер
0x14072bb5b: movzx edx, byte [rax+0x5e0] ; цвета волос/глаз (конверсия int->float)
...
```

Это подтверждает оффсет `+0x10` для PGD, но конкретная функция — сеттер
какого-то UI-параметра персонажа (byte-slider → float color), не код
сохранения. AOB встречается **один раз** в экзе (однозначный якорь), но
сама инструкция `mov rax,[BaseB]` используется отсюда в дереве вызовов
очень widely, так что для поиска именно save-write нужен другой якорь (см.
п.5 — тупик, или нужно искать иначе, например по вызовам `WriteFile`/
`CreateFileW` с фильтром по размеру буфера `~0x4204D0`/`0x60020`).

### 4. Pattern1 — почему он "не нравится"

Проверено на двух реальных сейвах пользователя (`Downloads/DRAKS0005.sl2`
от 27.08, `DRAKS0005 (1).sl2` от 01.11) — посчитано число совпадений P16
(`FF×4 00×4 FF×4 00×4`) в окне `[0x1F000, 0x1FFFF]` расшифрованного слота:

| слот | совпадений |
|------|-----------|
| 0 (старый сейв) | 68 |
| 0–8 (новый сейв, разные персонажи) | 48–86 |

Т.е. это не "якорь с редким совпадением", а повторяющийся через ~8 байт
заполнитель (похоже на таблицу с чередованием `-1 / 0` по 4 байта —
возможно, массив 32-битных ID/флагов с значением "не установлено" = -1).
Текущий код берёт **последнее** совпадение в окне и считает это базой для
костров/NG+/world-flags — работает только потому, что реальные данные
физически идут куда-то после этой таблицы-заполнителя, а не из-за того,
что сам паттерн уникален. Это согласуется с тем, что по DS3 написано в
`ds3-bonfire-anchor.md` (тот же P16, та же проблема, то же решение
"последнее вхождение + фиксированный относительный оффсет").

**Отсюда вывод для улучшения:** надёжнее искать не сам P16, а конец этой
таблицы заполнителей (переход от повторяющегося `FF×4 00×4` к реальным
данным) или валидировать найденную базу по структуре данных ПОСЛЕ неё
(как уже сделано для `findGestureTable()` — там идёт проверка структуры
записей, а не просто "нашли байты"). Это стоит сделать и для `findPattern1()`.

### 5. `.sl2` строка → тупик (диалог открытия файла)

Единственная xref на widestring `.sl2` (`VA 0x1415d9150`) — `VA
0x1410bf67a`, внутри конструктора объекта с несколькими `std::wstring`
подполями и числовыми полями-сентинелами (`0x80000000`/`0x80000001`).
По сигнатуре (COM: `CoCreateInstance`/`CoInitialize` в импортах +
структура `{имя-фильтра, "*.sl2"}`) это `COMDLG_FILTERSPEC` для
Windows `IFileDialog` — то есть код диалога "Открыть/Сохранить файл",
скорее всего мёртвый/отладочный (у DSR нет пользовательского file picker
для сейвов в обычной игре). Не ведёт к автосейву по ESC×2.

### 6. Seamless Co-op (`.co2`)

- `ds1sc_launcher.exe`: 193 КБ, импортирует только CRT + `KERNEL32`,
  единственные релевантные строки — `"SeamlessCoop"` и `"ds1sc.dll"`.
  Это просто загрузчик, который инжектит DLL; сам формат сейва не трогает.
- `SeamlessCoop/ds1sc.dll` (2.4 МБ): строки `"SL2"` — false positive
  (это часть `CALG_SSL2_MASTER`, константа Windows SChannel, не про сейвы).
  Нет строк `PlayerGameData`/`SaveLoad`/`.co2`/`.sl2`-путей. Скорее всего
  расширение `.co2` прописано в конфиге/коде как чистая замена строки при
  построении пути, без переработки формата — что согласуется с тем, что
  файл расшифровывается ровно тем же ключом/схемой, что и `.sl2` (см. TL;DR).
- Единственная полезная находка — кусок таблицы RTTI-имён игры, видимо
  скопированной мод-автором для валидации указателей при хуках:
  `NS_FRPG::PlayerIns`, `NS_FRPG::EcTest*` (EzState event-condition классы).
  Подтверждает нейминг: игровая логика в неймспейсе `NS_FRPG`, крипто — в
  `DLCR` (см. п.2).

## 7. Soulstruct (Grimrukh) — внешний открытый проект, НЕ про сейвы, но полезен

<https://github.com/Grimrukh/soulstruct> — Python-библиотека для парамов,
карт (MSB), EMEVD-скриптов, ESD/EzState, текста и т.д. для DS1/DS3/Bloodborne/
Elden Ring. **Не содержит ни одного модуля для `.sl2`/`.co2`** — проверено по
полному дереву репозитория (1274 файла), ни одного файла про сейвы. Это
подтверждает ожидание пользователя: не поможет напрямую с форматом сейва.
НО — полезно для дальнейшей работы с параметрами/флагами/картами:

### 7.1. Таблица костров (`darksouls1r/utilities/bonfire_warp_list.py`)

Авторитетный, перекрёстно проверенный список всех 21 костра DSR в порядке
меню варпа — `(event_flag, bonfire_entity_id, place_name_text_id)`:

```
200 Firelink Shrine        205 Sunlight Altar       203 Anor Londo
207 Chamber of Princess    208 Darkmoon Tomb        204 The Abyss
202 Daughter of Chaos      206 Altar of Gravelord   201 Stone Dragon
209 Sanctuary Garden       210 Oolacile Sanctuary   211 Oolacile Township
212 Chasm of the Abyss     213 Oolacile Twnshp Dng  214 Depths
215 Undead Parish          216 Painted World        217 Tomb of Giants
218 Duke's Archives        219 Crystal Cave         220 Catacombs (DSR-only)
```

**Кросс-проверка с `BONFIRE_BIT_INDICES`/`getBonfireWarpFlags()` в
`Character.ts`:** порядок **совпадает**, но зеркально — бит `23` у нас =
первый в списке Soulstruct (Firelink), бит `3` = последний (Catacombs).
То есть `наш_бит = 23 - soulstruct_display_index`. Проверено на нескольких
точках (Sanctuary Garden: idx 9 → бит 14 ✓; Oolacile Sanctuary: idx 10 →
бит 13 ✓; Oolacile Township: idx 11 → бит 12 ("Oolacile" в комментарии) ✓).
**Вывод: все 21 название/порядок в `Character.ts` подтверждены независимым
источником.** Не баг, просто биты читаются в обратном порядке (старший бит
байта `0x6D` = первый пункт меню).

Отдельно: сам список `(flag, entity, text)` зашит **в самом exe как
статичные данные** по фиксированному файловому смещению
`DSR_WARP_LIST_OFFSET = 28100512` (`0x1AC5020`) — это не связано с форматом
сейва (это таблица для меню "быстрый варп", читает event-флаги 200-220
из текущей игровой сессии, а не напрямую байты сейва), но подтверждает, что
"прямое смещение в exe без AOB" — обычная практика для таких таблиц.

### 7.2. Живая память (`darksouls1r/utilities/memory.py`, `memory_monitor.py`)

Для текущей версии DSR (`BASE_ADDRESS = 0x140000000`, совпадает с нашим
ImageBase) даёт **готовые фиксированные VA** (не AOB) для ключевых
указателей:

```
WORLD_CHR_BASE = 0x141D151B0
CURRENT_MAP    = 0x141D27D60
EVENT_FLAG_OFFSETS = (0x141D19950, 0, 0)
DRAW_PARAM_BASE (MemoryDrawParam) = 0x141D1C468
```

и живую структуру записи персонажа в мире (`WORLD_CHR_BASE` → список чаров
на карте, НЕ формат сейва, но полезно для будущих live-правок/валидации):

```
chr_address + 0x08  = handle_id (u32)
chr_address + 0x88  = model_name (10 wide chars, напр. "c0000")
chr_address + 0x3E8 = current_hp (u32)
chr_address + 0x3EC = max_hp (u32)
chr_address + 0x68  → map_info_address → +0x28 → transform_address:
    transform + 0x04 = facing_angle (float)
    transform + 0x10/0x14/0x18 = x/y/z (float)
```

Закомментированные в `BASE_POINTER_TABLE` AOB-паттерны (`WORLD_CHR_BASE`,
`CHR_CLASS_BASE`, `CAM_MAN_BASE` и др.) — тоже ценны как стартовые точки,
если нужно будет резолвить эти указатели в другой версии патча, где
зафиксированные VA уже не совпадут.

**Итог:** Soulstruct не даёт офсетов внутри `.sl2`, но даёт (а) независимое
подтверждение порядка/названий костров, (б) готовые якоря и структуру live
character-записи в памяти, которые пригодятся на этапе "что за что
отвечает" (флаги, парамы, карты) и для будущего memory-sweep (когда до него
дойдём).

## 8. "Идти от изменения стата" — нашли live apply-функцию (не save-writer, но важная находка)

Подход пользователя: вместо поиска самого save-writer искать код, который
вызывается ПОСЛЕ изменения характеристики, и идти от него. Сделал статически
(без живой игры): взял подтверждённый глобальный указатель `BaseB`
(`VA 0x141c8a530`), нашёл ВСЕ 773 места в exe, где на него ссылаются
(RIP-relative `mov`/`lea`), отфильтровал те, что делают `[reg+0x10]` сразу
после (= реально берут PGD, а не что-то другое через BaseB) — осталось 557 —
и для каждого посчитал, сколько РАЗНЫХ смещений `PGD+N` трогает его функция
(гипотеза: сеттер одного поля трогает 1-2 смещения, а функция сериализации
или "применить все статы" — трогает много и из разных семантических
областей).

**Топ-кандидат: `VA 0x1406981a0`** — трогает 13 разных смещений:
`0x40,0x48,0x50,0x58,0x60,0x68,0x70,0x80,0x84,0x88,0x90,0x94`. Дизассемблировал
целиком — это **не save-writer**, а функция "применить новые статы к живому
персонажу", вызываемая из экрана левел-апа (прокачки душами). Но она дала
железное подтверждение структуры и ОТКРЫЛА реальные игровые формулы:

```
rdx = указатель на структуру "новые статы" (поля по 4 байта, с шагом 0x04):
  rdx+0x00 -> PGD+0x40  VIT   (совпадает с файловым 0xA0, уже было известно)
  rdx+0x04 -> PGD+0x48  ATN
  rdx+0x08 -> PGD+0x50  END
  rdx+0x0c -> PGD+0x58  STR
  rdx+0x10 -> PGD+0x60  DEX
  rdx+0x14 -> PGD+0x88  RES   (!! в структуре идёт после DEX, но пишется в
                                 "дальнее" поле PGD+0x88 — ровно совпадает
                                 с файловым 0xE8, уже подтверждённым через
                                 комментарий COVENANT_OFFSET)
  rdx+0x18 -> PGD+0x68  INT
  rdx+0x1c -> PGD+0x70  FTH
  rdx+0x20 -> PGD+0x80 И PGD+0x84 (одно и то же значение пишется в оба поля —
                                     назначение не расшифровано, кандидат на
                                     "страховка"/дубль одного derived-поля)
```

Дальше функция читает/пишет ещё два поля через отдельную формулу с клампом
(`PGD+0x94`, `PGD+0x90` — вычисляются из разницы старого/нового значения
через поля параметра `rcx`/`r8` на `+0x29c`/`+0x2a0`/`+0x294`), а затем — если
есть живой `ChrIns` (другой указатель, не PGD, читается из ещё одного
глобального рядом с `[rax+0x68]`) — вызывает **настоящие игровые формулы**:

```
call 0x1402df9a0   ; формула от VIT  -> пишет в PGD+0x1c, читает ChrIns+0x3ec (= max_hp!)
call 0x1402dfa60   ; формула от ATN  -> пишет в PGD+0x24, читает ChrIns+0x3f4
call 0x1402dfcd0   ; формула от END  -> пишет в PGD+0x38, читает ChrIns+0x3f0/0x3f8
...
or byte [ChrIns+0x949], 8      ; флаг "пересчитать"
call 0x14035c280 / c510 / c6c0 / c740   ; ещё 4 пересчёта (экипировка/поиз/сопротивления?)
```

`ChrIns+0x3e8/0x3ec` под именами `current_hp`/`max_hp` **уже документированы
независимо** в `Soulstruct`'овском `memory_monitor.py` (см. раздел 7.2) —
совпадение подтверждает, что это тот же `ChrIns`, и что `0x1402df9a0` —
это, вероятно, НАСТОЯЩАЯ игровая формула VIT→HP (которую сейчас в редакторе
заменяет статичная таблица `VIT_TO_HP`). Не разобрал сами формулы (не хватило
времени), но адреса есть — можно продолжить при необходимости.

**Вызывающих всего 2** (`0x14069693c`, `0x140696db0`) — оба внутри одного
UI-контроллера экрана левел-апа: структура-источник статов лежит по адресу
`this+0x270` (сравнивается с "текущими применёнными" статами в `this+0x24c`),
и "применить" дёргается при подтверждении. **Ничего похожего на файловую
запись (`CreateFileW`/`WriteFile`/MD5/Rijndael) в цепочке вызовов нет** —
подтверждает, что в DSR смена стата и запись сейва НЕ связаны напрямую:
сейв происходит отдельно (по выходу в главное меню/при закрытии игры), а не
сразу после траты очков. Так что этот путь, хоть и дал отличную находку по
структуре/формулам, к save-writer'у не ведёт — там просто нет прямой связи.

## 9. Поиск по константам размера сейва — ложное срабатывание

Искал `0x60020` (`USER_DATA_SIZE`), `0x60030` (`SAVE_SLOT_SIZE`), `0x4204D0`
(`SAVE_FILE_SIZE`), `0x2C0` (`BASE_SLOT_OFFSET`) как 4-байтные LE-литералы.
`0x4204D0` — 0 совпадений. `0x2C0` — 496 совпадений (слишком частое маленькое

это byte-паттерн совпал внутри **встроенного юнит-тест-харнесса** (функция с
последовательными "номерами строк" `0x5ed, 0x5ee, 0x5ef, ... 0x623` и вызовами
ассертов) — не имеет отношения к сейвам. Остальные хиты `0x60020`/`0x60030`
лежат в `.rdata`, то есть это данные, а не код — не проверял, что это
(возможно, таблица размеров для разных платформ/версий, но не приоритет).

**Вывод:** прямой поиск по размерным константам не сработал как якорь —
слишком неоднозначно для автоматического фильтра по байтам без дизассемблера
с нормальным разбором функций (Ghidra/IDA дали бы это мгновенно через
"найти все функции, использующие эту константу", а не byte-grep).

## 10. `CreateFileW`/`WriteFile` xrefs — обобщённая файловая обёртка, тоже тупик

Во всём exe всего 4 места вызова `CreateFileW` и 4 — `WriteFile` (через IAT,
`call qword ptr [rip+disp]`, resolve по адресу слота в таблице импорта):

```
CreateFileW: 0x140994266, 0x1409a19fe, 0x140d045c1, 0x140d051df
WriteFile:   0x1409a1b46, 0x140d0570e, 0x140d05939, 0x140d7eeca
```

Все 4 пары лежат внутри **одной обобщённой обёртки файлового I/O**
(что-то вроде `File::Open`/`File::Write` с хендлом в `this+0x60`) — видно по
идентичной структуре пролога/эпилога в парах `(0x140d045c1,0x140d051df)` и
`(0x140d0570e,0x140d05939)`. Никаких строк-имён файлов или констант размера
рядом — путь и буфер приходят параметрами от вызывающего кода, а вызывающих
у такой обобщённой обёртки может быть огромное количество (логи, конфиги,
текстуры, сейвы — всё идёт через один `File`-класс). Чтобы понять, какой
вызов именно про `.sl2`, нужно смотреть по дереву вызовов ВВЕРХ до места,
где строится путь — а это именно то, для чего нужен нормальный декомпилятор
с построенным графом вызовов (Ghidra/IDA), а не byte-grep.

Пробовал зацепиться за строки `"NBGI"`/`"DARK SOULS REMASTERED"`
(юникод, найдены раньше, см. п.0) — ни одна не имеет прямых
`LEA`/`MOV [rip+disp]`-ссылок из кода вообще. Либо они читаются каким-то
другим способом (не прямой rip-relative адрессацией — например, через
таблицу смещений, которую я не нашёл), либо это мёртвые/ресурсные строки,
не используемые в рантайме для построения пути сейва.

**Итог по поиску оркестратора записи сейва:** чистый byte-pattern подход
(без полноценного автоанализа функций/графа вызовов) исчерпал свои дешёвые
зацепки — строки, константы размера, известные крипто-функции (MD5Init),
генерик file-I/O — каждая либо не ведёт туда, либо ведёт в код, не
относящийся к сейвам. Дальше без Ghidra/IDA (нет Java 17+/декомпилятора в
системе) или без живого дебага (разрыв на `WriteFile` в момент реального
сохранения через ESC×2, с просмотром call stack — метод, которым наверняка
нашли бы функцию за секунды) — продвигаться будет только медленнее и шумнее.

## 11. CT-файл пользователя (`1FRDarkSoulsRemastered.CT`) — PlayTime подтверждён живьём

У пользователя оказался реальный файл этой CT (не только комментарии о ней).
В нём группа **"Player Game Data"** содержит поля на **`BaseB` напрямую**
(ОДИН оффсет, без `+0x10`!) — это ДРУГОЙ объект, не `PGD`:

```
"Play Time"    : [BaseB]+0xA4   (4 Bytes)
"LanCutPoint"  : [BaseB]+0xAC   (Float)
"ClearCount"   : [BaseB]+0x78   (Byte)
"ClearState"   : [BaseB]+0x7C   (Byte, none/good/bad)
"Full Recover" : [BaseB]+0x80   (4 Bytes)
```

Т.е. `[BaseB]` сам по себе указывает на объект верхнего уровня, у которого
`PGD` — это ЕГО собственное поле на `+0x10` (`PGD = [[BaseB]+0x10]`, как и
было подтверждено ранее), а `PlayTime`/`ClearCount`/`FullRecover` — соседние
поля ТОГО ЖЕ объекта, не части `PlayerGameData`.

**Проверил дизассемблером** (искал xrefs к глобальной переменной `BaseB`
0x141c8a530, отфильтровал на прямой доступ `[reg+0xA4]` без промежуточного
`+0x10`) — всего **9 мест** во всём exe, все в одном районе
`0x140755000–0x140758cc0`:

- `0x140755...` — функция **сброса** состояния (новая игра): зануляет
  `+0x94,+0x98,+0xa4(PlayTime),+0xa8,+0xac`, ставит `+0x9c=-1`. Побочно
  подтверждает соседние поля (`+0x94..+0xac`) как единый "счётчики прогресса"
  блок.
- `0x140758c47` — **инкремент**: `PlayTime += (int)(xmm6 * const)` — перевод
  float delta-time в целые тики и накопление.
- `0x140758c6b` — **клэмп** на максимум `0xD693A018`.
- `0x140758ca0` — простой **сеттер** (`mov [rax+0xA4], ecx`).
- `0x140758cc0` — **конвертер** (`mul 0x10624DD3; shr edx,6` — умножение-сдвиг
  вместо деления, классический паттерн компилятора для перевода тиков в
  секунды/другую единицу).
- `0x140757e19` — **геттер**, кладёт `[BaseB+0xA4]` в out-параметр вызывающего.

**Тупик того же типа, что и раньше:** у геттера (область
`0x140757c40-0x140757e45`) **нет ни одного прямого (`E8`) вызова** во всём
exe. Внутри этой же функции видно почему: она сама дёргает соседние поля
через **виртуальный вызов** (`call qword ptr [rax+0x18]`, с разными `rdx`-
дескрипторами типа `+0x8c`/`+0x90` — похоже на generic
"GetParam(descriptor)" через интерфейс). Вызов САМОЙ этой функции отсюда —
скорее всего тоже через vtable (виртуальный метод), а не прямой `call`, так
что byte-pattern поиском (`E8 rel32`) его просто не видно — adresat не
хранится как плоский литерал, а резолвится через указатель на таблицу
методов в рантайме.

**Вывод:** та же стена, что и в разделах 8/10 — без настоящего
декомпилятора с анализом vtable (Ghidra/IDA умеют резолвить это
автоматически через RTTI/класс-анализ) byte-grep дальше не продвинется.
Решили подождать, пока Ghidra (см. ниже) доанализирует бинарник, и смотреть
"кто вызывает" через её собственный xref-браузер вместо ручного regex.

## 12. CT-файл пользователя — расшифровка конвенции и массовая сверка полей

У пользователя оказался реальный `1FRDarkSoulsRemastered.CT` (не только
комментарии о нём). Это валидный XML — распарсил `xml.etree`, не руками.

### 12.1. Конвенция офсетов CT (расшифровано и проверено)

`<Address>BaseB</Address>` + `<Offsets><Offset>A</Offset><Offset>B</Offset></Offsets>`
применяется **в обратном порядке документа**: все, кроме последнего офсета
в списке — это `addr = *(addr + offset)` (с разыменованием), а **первый**
офсет в списке — финальное `addr = addr + offset` **без** разыменования
(это и есть читаемое/пишемое значение).

Проверено на 100% совпадении с уже известными фактами:
- `VIT: BaseB->+0x40->+0x10` ⇒ `PGD = *(*(BaseB)+0x10)`; `VIT = PGD+0x40` —
  файл `0xA0` (`PGD+0x60`-сдвиг) — совпадает с `STATS_OFFSETS.VIT`.
- `Current Covenant: BaseB->+0x113->+0x10` ⇒ `PGD+0x113` — файл `0x173`,
  совпадает с `COVENANT_OFFSET` **в точности**.
- `Hp: BaseX->+0x3E8->+0x68` ⇒ `ChrIns = *(*(BaseX)+0x68)`; `Hp=ChrIns+0x3E8`
  — совпадает с `memory_monitor.py` (Soulstruct) `chr_address+0x3E8=current_hp`.

### 12.2. Attributes — 100% совпадение (доп. подтверждение)

`Soul Level = PGD+0x90` → файл `0xF0` (совпадает с `level`), и все 8 статов
совпадают байт-в-байт с `STATS_OFFSETS`.

### 12.3. Covenants — НОВОЕ: индивидуальные ранги/пожертвования по ковенанту


7 последовательных байт прямо перед `Current Covenant` — явно ранг/счётчик
пожертвований для каждого ковенанта (кроме Way of White и Princess's

### 12.4. "ClearCount"/PlayTime-блок — НЕ часть PGD, фиксированный офсет от BaseB

```
PlayTime      [BaseB]+0xA4   (уже разобрано в §11)
LanCutPoint   [BaseB]+0xAC   (float)
ClearCount    [BaseB]+0x78   (Byte) — это и есть NG+! DROPDOWN: 0=Journey1(NG) .. 5=Journey6
ClearState    [BaseB]+0x7C   (Byte) — none/good/bad
FullRecover   [BaseB]+0x80   (4 Bytes)
```

**NG+ в живой памяти — `[BaseB]+0x78`, не через PGD вообще.** Сейчас
`Character.ts` берёт NG+ как `findPattern1() - 0xBC0` (хрупкий байт-скан).
Важное концептуальное уточнение: AOB/pointer-chain (как в CT) работает
**только в живом процессе** — на уже сохранённый, расшифрованный файл на
диске его применить нельзя, указателей там нет, только плоские байты. Это
и есть причина, почему для офлайн-редактора в принципе нужен байтовый
якорь типа `Pattern1` — не ошибка подхода, а единственный вариант. Проблема
именно в том, что выбранный паттерн (`FF×4 00×4 ×2`) — общий филлер
(48-86 совпадений в окне поиска, см. §4), а не уникальная сигнатура.
**Следующий практический шаг** (не сделан): на реальных сейвах сопоставить,
на каком файловом расстоянии от конца инвентаря/PGD реально лежит этот
ClearCount-блок, и заменить скан фиксированным смещением (как уже сделано
для `GESTURE_TABLE_OFFSET`) — вместо правки самого `Pattern1`.

### 12.8. Bonfires/World Progression Flags — другой базовый указатель

Группа "Bonfires" идёт не через `BaseB`, а через **свой** символ
`ProgressionFlags`, который резолвится СВОИМ отдельным AOB
(`48 8B 0D ?? ?? ?? ?? 41 B8 01 00 00 00 44`, см. `autoAssemble` в начале
CT) — то есть это полностью независимый от `BaseB`/`PGD` указатель.
Структура — 3 байта с битовыми флагами (`+0x18`,`+0x19`,`+0x1A`, 8 бит
каждый = 24 бита на ~21 костёр) плюс `Unlock Warps` на `+0x5B` — та же
трёхбайтовая раскладка, что уже реализована в `Character.ts`
(`BONFIRE_RELATIVE_OFFSET_1/2/3` + `BONFIRE_RELATIVE_FLAG_OFFSET`), просто
через другой (живой, не файловый) путь резолва. Порядок костров внутри
байтов в CT не удалось сразу сверить бит-в-бит с текущим кодом (не хватало
атрибута `<Bit>` в моём дампе) — но названия/количество уже независимо
подтверждены через Soulstruct (§7.1), этого достаточно.

## 13. Разметка "мёртвой зоны" между инвентарём и `Pattern1` (на реальных сейвах)

Диффил `0xE498`→`0x1E4A8` (разрыв после блока внешности до таблицы жестов)
и `0x1E4E4`→`0x1F400` (после таблицы жестов до зоны, где сейчас падает
`Pattern1`) по **11 реальным персонажам** из трёх файлов пользователя
(`Downloads/DRAKS0005.sl2`, `DRAKS0005 (1).sl2`, `DRAKS0005.co2`) — искал,
какие байты вообще когда-либо отличаются между персонажами (у статичных
полей/паддинга — никогда).

### 13.1. `0xE498`–`0x1E4A4`: фиксированный массив 2048×32 байта — **Бездонная коробка** (Bottomless Box)

Подтверждено пользователем: это хранилище в Firelink Shrine, параллельное
основному инвентарю (отсюда и совпадение количества слотов — 2048). Не
мировые флаги, не нужно для текущей задачи — у большинства тестовых
персонажей пусто, потому что они туда ничего не складывали; заполнено
только у реально играных (`Everything`, `The Scavenger`).

99% байт здесь одинаковы у ВСЕХ персонажей и равны `FF×8 00×4 FF×4 00×...`
— это и есть источник многочисленных совпадений `Pattern1` (см. §4): это
значение "пустой" записи вот этой таблицы, не какой-то специальный маркер.

- Начинается в `0xE4A4` (12 байт заголовка после блока внешности), запись —
  **32 байта**, **2048 записей** (тот же счётчик, что `MAX_SLOTS` у
  инвентаря — наводит на мысль, что это параллельный инвентарю массив, по
  записи на слот). Кончается ровно в `0x1E4A4`, за 4 байта до фиксированной
  таблицы жестов (`0x1E4A8`) — **без зазора**, т.е. это не "мусор", а чётко
  посчитанный блок.
- У большинства персонажей (включая explicitly дублированные тест-слоты
  через `slotDuplicator`) ВСЕ 2048 записей — "пусто". Только у двух реально
  поигранных персонажей (`Everything`, `The Scavenger`) часть байт записи
  заполнена чем-то вроде ID (разобрано частично, назначение не установлено).
- **Вывод:** именно заполненность ЭТОЙ таблицы (не размер инвентаря, не
  уровень) определяет, сколько "заполнителя" `FF×4 00×4` останется до конца
  таблицы — отсюда и "гуляющий" `Pattern1`, который сканирует именно внутри
  неё по значению, а не по границе.

### 13.2. `0x1E4E4`–`0x1F400`: цепочка блоков с чёткими структурными границами

```
0x1E4E4-0x1E4E7   (4 байта, похоже на фиксированные/заголовок)
0x1E4E8           1 байт, варьируется (назначение не ясно)
0x1E4F0-0x1E5C8   таблица коротких записей, 4 байта/запись (~3 из 4 байт меняются)
0x1E5C8-0x1E6FA   один большой варьирующийся блок (~306 байт, без видимой под-структуры — гипотеза: боссы/NPC)
0x1E6FA-0x1EE5A   РЕГУЛЯРНАЯ таблица, 16 байт/запись, ~113 записей
                  (12 из 16 байт каждой записи варьируются — вероятно
                  world event flags, см. getWorldEventFlag() в Character.ts)
0x1EE5A-0x1F2AE   большой непрерывно варьирующийся блок (1109 байт) —
                  СЮДА физически попадают текущие bonfire_bytes_abs/ngplus_abs
                  (найденные через Pattern1+относительные офсеты у всех 11 персонажей)
0x1F2B0-0x1F3EC   мелкие нерегулярные варьирующиеся кусочки (хвост той же зоны)
```

Границы между блоками **структурные и стабильные** — не зависят от
прогресса игрока, только содержимое внутри каждого блока меняется. Это
подтверждает план из обсуждения с пользователем: искать не байтовый
паттерн, а идти от гарантированно фиксированной точки (конец таблицы
жестов, `0x1E4E4`) вперёд через эти границы — а не сканировать содержимое
на совпадение с `FF×4 00×4`.

**Не сделано (следующий шаг):** точно разобрать записи блока `0x1E6FA-
0x1EE5A` (вероятные world-флаги) и найти точную, детерминированную границу
входа в блок `0x1EE5A-0x1F2AE` (где реально лежат костры/NG+/warp-флаг) —
это должно заменить текущий скан `Pattern1` на точный фиксированный
относительный офсет от конца таблицы жестов.

## Что пробовал и почему не пошло

- **radare2** (скачанный `.exe` для headless-декомпиляции): харнесс
  заблокировал запуск скачанного стороннего бинарника — это правильное
  поведение, не стал обходить. Альтернатива — `pefile`+`capstone` (чистый
  Python, установлен через pip), ею и пользуюсь.
- **Ghidra**: нет Java 17+ в системе (есть только Java 8), не стал тянуть
  отдельный JDK ради этого — текущий подход (точечный дизасм вокруг
  найденных литералов/RTTI-строк) оказался достаточным для подтверждения
  конкретных фактов без полного автоанализа гигантского бинарника.
- **AES-ключ как литерал**: искал как цельный 16-байтный блок (прямой и
  реверснутый порядок байт, байт-swap по словам) — нигде не нашёл, см. п.1.
- **RTTI Complete Object Locator** для `DLRijndaelAlgorithm` → vtable:
  начал, не довёл до конца (см. "Следующий шаг" в п.1).

## Инструментарий сессии

Все скрипты временные, лежат в scratchpad сессии (не в репозитории):
`pefile` для разбора PE/секций, `capstone` для дизасма x64,
`pycryptodome` для AES-CBC расшифровки `.sl2`/`.co2` при проверке гипотез.
Полезные паттерны поиска, которые сработали:
- RIP-relative `LEA`-xref: byte-pattern `[REX][0x8D][ModRM&0xC7==0x05][disp32]`,
  резолв `target = addr_after_insn + disp32`.
- Near `CALL`-xref: byte-pattern `0xE8[rel32]`, резолв аналогично.
- Кластеризация нескольких известных constant-слов в окне ~0x100 байт —
  быстро находит инициализацию структур (сработало для MD5 IV).
