# DS3 Appearance Sweeper

Ищет, **где в сейве DS3 лежат данные внешности персонажа**, чтобы сделать в
редакторе вкладку Appearance — такую же, как в DS1. Родня `ds3-gesture-sweeper`,
но приём другой и куда дешевле.

**Статус: задача решена.** Офсеты найдены и проверены, алгоритм поиска годится
для редактора — см. «Результат».

## Откуда взяты офсеты памяти

Из `DS3_TGA_v3.4.0.CT`, группа `Appearance` и скрипты
*Save / Restore Current FaceData* и *Save to file*. Таблицу ведёт команда
[The Grand Archives](https://github.com/The-Grand-Archives/Dark-Souls-III-CT-TGA);
у этих скриптов автор в таблице не указан (в отличие от соседних — там стоит
`//Author:`).
Границы блоков заданы прямо в них:

```
PlayerGameData (PGD) = [[GameDataMan]+0x10]

misc = PGD + 0x0AA,   4 байта    gender, voice, (class на +0x0AE)
body = PGD + 0x3B0,  28 байт     7 float — пропорции тела
face = PGD + 0x6B8, 192 байта    причёска/лицо/цвета/косметика/телосложение
```

Таблица из 129 полей (`FIELDS` в `constants.py`) сгенерирована из CT скриптом
`_gen_fields.py` — его же гоняй, если таблица обновится.

### Про лицензию

Переиспользуются **офсеты и раскладка структуры** — это факты об игре, не
авторский текст. Код таблицы (Lua, Auto Assembler, сам XML) не копировался: всё
здесь написано с нуля на Python. Подписи полей в редакторе будут переписаны — в
CT они с опечатками (`Chekbone Depth`, `Nose Ridge Lenght`) и без перевода.

Кредит: *DS3_TGA v3.4.0*, таблица The Grand Archives.

## Чем отличается от gesture-sweeper

У жестов флаг — один бит, все записи в таблице выглядят одинаково, и выделить
их можно было только изоляцией: 43 сейва по 9 МБ.

Внешность лежит сплошным блоком, и блок ищется в расшифрованном слоте **простым
побайтовым совпадением с памятью** — ноль записей в игру, ноль сейвов
(`--locate`). Записи нужны только как доказательство, что найденное место — то
самое, а не копия.

## Требования

```bash
pip install -r requirements.txt      # pymem, pycryptodome
```

Игра запущена, персонаж **загружен в мир** (не в главном меню), окно в
window/borderless режиме.

## Использование

```bash
python main.py --list                  # слоты сейва
python main.py --read                  # внешность из памяти (только чтение)
python main.py --locate                # найти блоки в текущем сейве (без записи)
python main.py --locate --slot 5 --values

python main.py --sweep --slot 5 --out ./out          # маркерный прогон, 3 сейва
python main.py --per-field --slot 5 --out ./out      # изолирующий, сейв на поле
python main.py --per-field --only lip_size,eye_size
python main.py --analyse-only --out ./out

python anchors.py [файл.sl2 ...]       # подбор якоря по всем профилям
python main.py --watch-ids --seconds 90    # снять список ID, листая меню внешности
python main.py --watch-region --seconds 60 --label age   # какой байт меняет настройка
python main.py --watch-region --region-start 0x6B8 --region-size 4 --all-changes
python main.py --export-preset me          # .ds3chr из памяти
python main.py --import-preset me.ds3chr  # и обратно
```

`--slot` задавай явно: при **дефолтном пресете** внешность одинакова у нескольких
персонажей, и face-блок находится сразу в нескольких слотах.

### Маркерный прогон (`--sweep`)

1. сейв как есть → `before.bin`
2. каждому безопасному полю своё уникальное значение (`k*7+13`, шаг 7 взаимно
   прост с 256 → значения не повторяются) → сейв → `marker.bin`
3. возврат исходных значений → сейв → `after_restore.bin`
4. `diff.py` строит `report.md`

Уникальность значений и даёт разложение 1:1 за один проход. Перебор по одному
полю (`--per-field`, сейв на поле) остаётся как способ разрешить неоднозначность.

## ВАЖНО: что писать нельзя

**В блоке лежат не только ползунки 0..255.** Часть полей — ИНДЕКСЫ моделей
(u32), и произвольное значение = запрос несуществующего ассета → **игра
вылетает** (проверено: первый `--sweep` уронил DS3).

| PGD | поле | диапазон |
|---|---|---|
| `0x0AA` | Gender | 0..1 |
| `0x0AB` | Voice | 0..2 |
| `0x0AE` | Class | 0..9 |
| `0x6B8` | Age | неясно, см. ниже |
| `0x6BC` | Hair Style | `0..11`, `101..112` |
| `0x6C0` / `0x6C4` | Left / Right Pupil | `0..8` |
| `0x6C8` | Brow Style | `0..16` |
| `0x6CC` | Beard Style | `0..11` |
| `0x6D4` | Tattoo/Mark | `0..55` без 6 значений |
| `0x6D8` | Eyelashes Type | `0..3` |

Перечислены в `constants.ID_FIELDS`, прогоном **не трогаются**: из 129 полей
пишутся 111, остальные 18 — ID и runtime. Их положение и так известно, маркеры
им не нужны.

В редакторе у этих полей должен быть **выпадающий список**, а не свободный ввод.

### Список допустимых ID — снят с игры

Гадать не пришлось: `--watch-ids` опрашивает поле каждые 15-20 мс, пока список
листают в меню внешности игры. Превью пишет выбор прямо в PlayerGameData (при
листании причёсок шевелился ровно байт `+0x04`), так что каждое значение здесь —
то, которое игра выставила сама.

| поле | значений | ID |
|---|---|---|
| Hair | 24 | `0..11` и `101..112` — **две семьи**, не один диапазон |
| Eyebrows | 17 | `0..16` |
| Beard | 12 | `0..11` |
| Left / Right Pupil | 9 | `0..8` |
| Eyelashes | 4 | `0..3` |
| Tattoo / Mark | 50 | `0..55` **без 11, 12, 16, 19, 31, 46** |
| `+0x00` | 12 | не ID, а три настройки в разрядах — ниже |

Дырки в списке татуировок настоящие: два независимых прохода по всему списку
дали одни и те же 50 значений и одни и те же шесть пропусков. Наивный диапазон
`0..55` предложил бы шесть несуществующих ID.

### «Pupil» — парный контрол, а не третье поле

В создании персонажа глаз три настройки: `Pupils`, `Left Pupil`, `Right Pupil`.
Третьего поля в памяти нет: «Pupils» пишет **оба глаза сразу** — и форму
(`face+0x08` и `+0x0C`), и цвет (`face+0x2C` и `+0x30`), всегда одним значением.
Проверено `--watch-region --all-changes`: обе тройки цвета менялись синхронно,
байт в байт. Редактор даёт такой же парный контрол поверх двух настоящих полей,
и показывает «mixed», когда глаза различаются.

### `+0x00` — это не ID, а три настройки в одном байте

CT зовёт этот байт Age и обещает 0..3, из-за чего в живых сейвах он выглядел
бессмыслицей: 0, 1, 100, 110, 111, 112. На деле в нём упакованы **три разные
настройки создания персонажа, по десятичным разрядам**:

```
значение = 100 * мускулистость + 10 * волосы_на_груди + возраст   (возраст 0..2)
```

Каждый разряд проверен отдельно в редакторе персонажа, и каждый переключатель
трогает только свой:

| настройка | разряд | наблюдение |
|---|---|---|
| мускулистость | сотни | `112 ↔ 12`, шесть переключений подряд |
| волосы на груди | десятки | `112 ↔ 102`, шесть переключений подряд |
| возраст | единицы | `0 / 1 / 2` |

Отсюда 12 допустимых значений, а не «шесть непонятных ID». В редакторе это три
отдельных контрола (выпадающий список возраста и два флажка), а не число.

Нашлось это режимом `--watch-region`: он слушает кусок PGD целиком и печатает,
какой байт шевельнулся. Им же подтвердился **голос** — `PGD+0xAB`, ровно три
значения `0/1/2` (до этого офсет был только правдоподобным: во всех 99
персонажах там лежал 0, потому что голос никто не менял).

## Результат (2026-09-12)

Прогон: профиль `011000013017fff9`, слот 5, DS3 в мире.
Анализ якорей: **99 персонажей из 15 файлов** (4 профиля + бэкапы редактора).

### Что где лежит

- **face-блок пишется в сейв целиком и побайтово.** 192 байта из памяти
  совпали один-в-один, **и хвост после них тоже — 16 из 16**. Значит структура
  это `PGD+0x6B8 .. +0x787` = **208 байт**, а CT-шные 192 её обрезают.
  Хвост доказан отдельно: после падения игры в нём остался маркерный мусор,
  и следующий сейв записал в слот именно его.
- **Сверка значений память ↔ сейв: 122 из 122.** Расшифровка полей по CT верна.
- **Маркерный прогон: 111 из 111 полей доехали до сейва**, внутри блоков
  изменилось ровно 111 байт, восстановление побайтовое.
- **body-блок (28 байт float) в сейве не найден ни разу.** Пропорции тела
  хранятся в face-блоке байтами `0x704..0x70A` («Build Detail»), а float'ы в
  `PGD+0x3B0` — их runtime-развёртка.
- **gender/voice лежат не в face-блоке, а в блоке статов**, от якоря
  `CHARACTER_PATTERN`: gender `-0xA6`, voice `-0xA5`. Сходится с уже известным
  редактору `CLASS = -0xA2` (в памяти class на 4 байта дальше gender). Gender
  по всем 99 персонажам принимает только 0/1; voice везде 0 — офсет
  правдоподобен, но не доказан, никто не менял голос.

### Внутренняя раскладка face-блока

```
+0x00..0x23  девять u32 — «детали»: телосложение+возраст, hair, pupilL, pupilR,
             brow, beard, ?, tattoo, eyelashes (значения маленькие => старшие
             3 байта нули)
+0x24..0x47  девять RGBA В ТОМ ЖЕ ПОРЯДКЕ: кожа, hair, pupilL, pupilR, brow,
             beard, ?, tattoo, eyelash (альфа везде ff)
+0x48..0x4B  позиция / угол / размер татуировки
+0x4C..0x52  Build Detail — 7 байт пропорций тела
+0x66…       ползунки формы лица
```

### Шестая пара — неиспользуемый слот

ID и цвета — два параллельных списка в одном порядке, то есть каждый индекс это
«деталь + её цвет». Шестая пара (`+0x18` и `+0x3C`) не опознана, и, похоже,
опознавать нечего: у **всех 82 персонажей** там `ID = 0` и цвет `00 00 00 ff`,
без единого исключения, и ни один прогон в редакторе персонажа её не тронул.

Для сравнения соседняя татуировка живёт: встречаются `ID = 20` и `55`, а у двух
персонажей ID нулевой при цвете `0a 64 64 ff` — то есть цвет остаётся, даже
когда деталь выключена. Так выглядит используемый слот; у шестого не так.

Проверена и версия «это выбранный пресет лица»: переключение готовых пресетов
переписало **81 байт** блока — и этой пары среди них нет. Игра перекраивает лицо
целиком и всё равно её не трогает.

Редактор его не показывает: смысл неизвестен, допустимые ID неизвестны, а
произвольный ID модели роняет игру.

### Три безымянных поля, которых нет в CT

Тот же прогон по пресетам нашёл байты, которых таблица не знает, а игра ими
пользуется: **`face+0x91`, `+0xAB`, `+0xAC`**. `0x91` стоит между Lip Protrusion
и Mouth Protrusion, `0xAB`/`0xAC` — прямо перед Cheek Color.

Всего в блоке 49 байт не описаны ни одним полем CT; пресеты подвинули из них
ровно эти три, остальные 46 не шелохнулись. Три добавлены в редактор группой
`Unlabelled` — без них он не смог бы воспроизвести лицо, которое умеет игра.

### Как искать блок в редакторе

Абсолютный офсет **плавает** — и между персонажами, и между двумя сейвами
одного персонажа (на `0x190C8` в одном сейве стоял face-блок, а тремя минутами
раньше по тому же адресу лежала таблица жестов). Поэтому как с кострами:

| якорь | разброс дельты | годен |
|---|---|---|
| `bonfire_block` | −0xA153 … −0xA337 (**0x1E4**) | **да** |
| `character_pattern` | 0x270 на «нормальных» сейвах, дальше расходится | нет |
| `inventory_start` | 0x364 и хуже | нет |
| `steamid` | гуляет, у части слотов ID вообще нет | нет |
| `absolute` | гуляет | нет |

Алгоритм (`sl2.find_face_block`, эталон для порта в TS):

1. грубая оценка = `findBonfireBlock() + FACE_COARSE_FROM_BONFIRE` (−0xA245);
2. поиск **структурной сигнатуры** в окне ±0x800 вокруг неё;
3. полный скан как фолбэк, берём кандидата ближе всех к оценке.

Сигнатура — сама структура блока, память для неё не нужна: девять u32 подряд с
нулевыми старшими байтами (`+0x00..0x23`) плюс девять байт `0xFF` на позициях
альфы (`+0x27`, `+0x2B`, … `+0x47`). Это 27 нулей и 9 `FF` в жёстко заданных
местах.

**Проверка: 99 из 99.** В окне всегда ровно один кандидат, до полного скана дело
не дошло ни разу; при ±0x200 результат тот же, так что запас бесплатный.

### Копии face-блока в слоте

По всему слоту сигнатура даёт и другие совпадения — пачками с шагом **0x1B8**
(до 40 штук у прокачанного персонажа). Похоже на кэш внешности встреченных
игроков. Оконный поиск их отсекает; полным сканом пользоваться нельзя.

При **дефолтном пресете** первые 192 байта совпадают у разных персонажей, так
что «искать по всему файлу и брать первое совпадение» неверно вдвойне — слот
должен быть задан.

## Формат пресетов — `.ds3chr`

Свой бинарник по образцу DS1 (`preset.py`), 216 байт:

```
0x00   4   магия "D3CH"
0x04   1   версия = 1
0x05   1   gender
0x06   1   voice
0x07   1   резерв
0x08 208   face-блок как есть
```

Всё значимое лежит в face-блоке, поэтому потерь нет по определению. `.dsrchr`
от DS1 заголовка не имеет, потому что подстраивается под чужой инструмент;
здесь формат наш, и магия нужна, чтобы `.dsrchr` не подсунули в DS3.

**Формат CT сознательно не используется.** Он режет facedata до 192 байт и
теряет хвост `0x778..0x787` — те самые 10 полей (Lipstick 1/2, Laugh Lines,
Nasal Size, Nose Bridge Color, Skin Tone, Skin Color Layer 1–4). А `<body>` в
нём — незаписываемая runtime-развёртка.
